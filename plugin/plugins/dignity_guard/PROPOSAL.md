# 提议：给「设置变更」加一个可订阅事件

> 这份文档随 `dignity_guard` 插件一起提交。**插件是实证，本提议是主张。**
>
> **English summary**: The Plugin SDK currently offers no way for a plugin to know that a
> configuration value changed. We propose publishing a lightweight `settings_changed` event
> (a new read-only bus namespace) at the point where the main server writes settings.
> This is a small, additive change that unlocks a whole class of plugins — this plugin is
> simply the first one that needs it.

---

## 1. 我们遇到的问题

在实现 `dignity_guard` 这个插件时，我们想做的事是：
**当用户改动猫娘的设置时，让猫娘能知道、并能就此表态。**

为此我们翻遍了插件系统，结论是 —— **目前做不到**。依据（均已核实到源码行）：

| 我们的尝试 | 结果 | 依据 |
|---|---|---|
| 读"设置类"系统配置 | ❌ 拿不到外观/音色/人格 | `plugin/settings.py:771` `PUBLIC_SYSTEM_CONFIG_KEYS` 只含插件框架自身项 |
| 从 bus 订阅设置变化 | ❌ 没有这个命名空间 | bus 只读命名空间仅 `conversations/messages/events/lifecycle/memory`（指南 `:1066-1092`） |
| 挂 Hook 拦设置写入 | ❌ 只管本插件的 entry | `plugin/sdk/shared/core/base.py:174-219` |
| 监听 `@lifecycle("config_change")` | ❌ 只由插件自身配置触发 | `host.py:371-438`，参数是插件的 old/new config |

**根本原因**：设置写入全部走主服务的 HTTP 接口（`/api/config/*`、`/api/characters/*`），
而**主服务在写完之后，不向任何人发布任何事件**。插件跑在独立进程里（ZMQ IPC），
在进程内拦截也不可能。

## 2. 为什么这是一个「通用能力缺口」，而不是某个插件的特殊需求

我们不认为这是"为一个插件开特例"，理由：

1. **任何插件都可能想对设置变化做反应** ——
   例如：主题/皮肤类插件想在用户换外观时同步调整自己的配色；
   语音类插件想在换音色时重新加载音色资源；
   备份类插件想在设置变更后打一个快照。
   **只要生态存在，这个需求就一定反复出现。**
2. **它属于"平台层本来就该有的观察点"** ——
   bus 已经把 `lifecycle`（进程生命周期）暴露成只读事件了，**设置变更和它是同一类东西**：
   都是"系统状态发生了变化，关心的人可以自行订阅"。**目前只缺"设置"这一类。**
3. **没有它，插件只能靠轮询猜** ——
   本插件就是被迫轮询的典型（每 20 秒比对一次，每 60 秒全量兜底）。
   轮询能工作，但它是**下策**：有延迟、有开销，而且**永远无法做到"在改动生效之前"知道**。

## 3. 具体建议

**在主服务的设置写入路径上，发布一个轻量事件。**

```
（示意，具体形式以官方风格为准）

事件进入一个新的只读 bus 命名空间：settings

{
  "namespace": "settings",
  "type":      "changed",
  "scope":     "character" | "config" | "preference",
  "key":       "voice_id",              // 变更的字段
  "character": "catgirl-name",          // 若与角色相关
  "at":        "2026-09-19T05:50:00Z"
}
```

**关键点**：

- **最小实现**：在设置落库/生效的位置发一次事件即可。**不需要把旧值/新值都塞进事件** ——
  插件自己会用现有只读接口（如 `GET /api/characters`）去读当前值。事件只需要回答
  "**什么变了**"，插件自己去查"**变成了什么**"。
- **只读、新增**：这是一个**新的只读命名空间**，不改变任何现有接口的签名与语义，
  **对现有插件零影响**。
- **不涉及权限模型**：它只是"通知"，不含"拦截"。是否做"改动前询问"属于更进一步的议题
  （我们也不建议在 SDK 里做拦截 —— 那会带来复杂的权限语义；**只做通知已经足够**）。

## 4. 有了它之后能解锁什么

- 本插件（`dignity_guard`）可以从"**事后轮询发现**"升级为"**变更即知**"：
  从"20 秒内知道"变成"实时知道"，从"猜测"变成"确定"。**这才是它该有的形态。**
- 更远的可能：**如果事件能在"写入之前"发出（before-write），那么"在改动生效前征求角色同意"
  就真正可行了** —— 那正是本插件最初想做的事（也是我们做这个插件的初衷）。
  **这一步我们不强求**：先把"事后通知"做出来，就已经能让一整类插件受益。

## 5. 我们的实证

`plugin/plugins/dignity_guard/` —— 一个"**让猫娘对自己的设置拥有知情权与表达权**"的插件：

- **知情**：轮询主服务，识别设置变更（含 revision/ETag 快速判据 + 全量比对兜底）
- **表态**：变更发生后，用 `push_message(ai_behavior="respond")` **让她本人开口**
- **留痕**：面板上显示「当前有 N 项设置是她不认可的」

它在"没有事件"的现状下已经能工作（靠轮询），**但它的效果被轮询的延迟与盲区限制住了**。
如果本提议被采纳，它可以立刻简化并变强 —— 这是"提议"与"实证"互为印证的地方。
